# dbug-appsec-masvs (Gate G5: AppSec Profile)

Zero-trace commercial mobile application penetration testing, OWASP MASVS (MASVS-CRYPTO, MASVS-NETWORK) cryptographic hygiene auditing, and automated OpenAPI 3.0 specification synthesis.

---

## 1. Operational Rationale

Commercial applications (banking, fintech, e-commerce, digital identity) implement heavy RASP (Runtime Application Self-Protection) and strict certificate pinning:
- Traditional intercepting proxies (Burp Suite, OWASP ZAP) get rejected because the app refuses custom CA certificates or detects proxy properties.
- Traditional dynamic instrumentation (Frida, Xposed) gets detected by native anti-tamper libraries (Promon, DexGuard, AppSealing) scanning `/proc/self/maps` and `TracerPid`.

`dbug` solves this by:
1. Intercepting decrypted HTTPS traffic out-of-band via Linux kernel eBPF uprobes on Conscrypt `libssl.so` (bypasses pinning without modifying the app or installing CAs).
2. Masking system properties via `resetprop` (`ro.debuggable=0`, `sys.usb.state=mtp`).
3. Providing an interactive human-in-the-loop mode (`--interactive`) so security auditors can log in, perform MFA, and navigate protected views while zero-trace capture runs.

---

## 2. OWASP MASVS Cryptographic Audit (MASVS-CRYPTO)

The AppSec auditor analyzes cryptographic buffer dumps from `instrumentation_events.jsonl` (generated by `crypto_dumper.js`):

| Finding Type | Condition / Pattern | MASVS Rule | Severity |
| :--- | :--- | :--- | :--- |
| **Insecure Cipher Mode** | `AES/ECB` (no initialization vector) | MASVS-CRYPTO-1 | HIGH |
| **Static Hardcoded IV** | Zero-filled IV (`0000...`) or repetitive bytes | MASVS-CRYPTO-2 | HIGH |
| **Deprecated Cipher** | `DES`, `3DES`, `RC4`, `Blowfish` | MASVS-CRYPTO-1 | HIGH |
| **Weak Hash Algorithm** | `MD5`, `SHA-1` used in signature/integrity checks | MASVS-CRYPTO-1 | MEDIUM |
| **Cleartext Transmission** | Unencrypted `http://` API communications | MASVS-NETWORK-1 | HIGH |

---

## 3. Automated OpenAPI 3.0 Specification Synthesis (`openapi_spec.json`)

The auditor inspects every intercepted HTTP request and response from `decrypted_http_requests.jsonl` and synthesizes a standards-compliant OpenAPI 3.0 JSON specification:
- **Paths & Methods:** Groups requests by host, path template, and HTTP method (`GET`, `POST`, `PUT`, `DELETE`).
- **Query Parameters:** Identifies parameter names, sample values, and infer types (string, integer, boolean).
- **Request Headers:** Captures custom authorization headers (`Authorization: Bearer ...`, `X-App-Token`).
- **Request Bodies:** Parses JSON payloads to synthesize JSON schemas for request bodies.
- **Immediate Tooling Interoperability:** The resulting `openapi_spec.json` can be directly imported into:
  - **Burp Suite:** Via OpenAPI Parser extension for automated scanning.
  - **Postman:** For collection generation and automated endpoint regression.
  - **OWASP ZAP:** For automated API vulnerability scanning.

## 4. Execution Workflow

```bash
# Run AppSec profile in interactive penetration-testing mode
python3 orchestrator.py \
    --package com.example.fintech \
    --profile appsec \
    --interactive

# Or run headless against an automated run
python3 parser_correlator/appsec_auditor.py \
    --session-dir sessions/session_<id> \
    --package com.example.fintech
```

### Deliverables:
- `API_SECURITY_REPORT.md`: Comprehensive OWASP MASVS assessment and API inventory.
- `openapi_spec.json`: Valid OpenAPI 3.0 specification for automated fuzzing.
- Synchronized to `targets/<target_id>/API_SECURITY_REPORT.md` and `openapi_spec.json`.
